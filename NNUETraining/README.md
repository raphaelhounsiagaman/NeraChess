# NNUE Training

Training pipeline for the NeraChess NNUE evaluation network. The engine-side
inference library lives in [`../NeraChessNNUE`](../NeraChessNNUE); this project
owns everything that produces a `.nnue` file the engine can load.

> **Status: working, untrained.** The loop runs end to end and needs no
> external engine, but no network is committed to the repository. See
> [`../docs/NNUE.md`](../docs/NNUE.md) for how the bootstrapping works.

## Layout

| Module | Needs PyTorch | Purpose |
| --- | --- | --- |
| `architecture.py` | no | Network shape, mirrored from `NetworkArchitecture.h` |
| `features.py` | no | Feature indexing, mirrored from `FeatureSet.cpp` |
| `serialize.py` | no | The `.nnue` container, mirrored from `NetworkFormat.h` |
| `quantize.py` | no | Float parameters to int16, plus a reference forward pass |
| `engine.py` | no | UCI client for a built `NeraChessUCI` binary |
| `dataset.py` | no | Training samples, feature caching, and batching |
| `model.py` | yes | The PyTorch model |
| `loss.py` | yes | The training objective |
| `train.py` | yes | Training entry point |
| `verify.py` | no | Checks the engine and the trainer agree on a network |

Only the model, loss, and trainer need PyTorch. Everything required to read,
write, and verify a network runs on the standard library, so the format stays
testable in CI without a heavyweight install.

## The duplication is deliberate

`architecture.py` and `features.py` restate constants and index arithmetic that
already exist in C++. They are duplicated rather than generated because the
engine needs them at compile time.

That duplication is only safe because it is checked:

* `tests/test_architecture.py` compares `architecture_hash()` against the value
  the engine emits, so any constant that drifts fails the suite.
* `tests/test_features.py` compares this package's indices against
  `tests/feature_vectors.json`, generated by the engine itself.
* `nnue_training.verify` compares the reference forward pass against the
  engine's `eval` output, position by position.

If the trainer and the engine ever disagree about the network, one of those
three fails. Without them the failure mode is a network that trains beautifully
and plays terribly.

## Running the tests

No dependencies required:

```bash
python3 -m unittest discover -s tests -t .
```

Regenerate the feature fixture after any change to the feature set:

```bash
../bin/Release/NeraChessTests/NeraChessTests --nnue-feature-vectors > tests/feature_vectors.json
```

## Exercising the pipeline without training

A network of random weights is enough to check that export, loading, and
evaluation all line up:

```bash
python3 scripts/make_random_network.py --output /tmp/random.nnue
```

```bash
python3 -m nnue_training.verify --network /tmp/random.nnue --engine ../bin/Release/NeraChessUCI/NeraChessUCI
```

Every position must report `ok`. A disagreement means the trainer and the
engine do not implement the same network, and no amount of training will fix
it.

## Training

Install the extras first:

```bash
pip install -r requirements.txt
```

Then train from a sample file:

```bash
python3 -m nnue_training.train --data data/positions.txt --output nera.nnue
```

Samples are plain text, one position per line:

```text
<fen> | <score> | <result>
```

`score` is the engine's evaluation in centipawns from the side-to-move point of
view, and `result` is the game result from the same point of view (`1.0` win,
`0.5` draw, `0.0` loss).

## Getting training data

Training data comes from self-play and nothing else — no external engine labels
any position, ever.

The bootstrapping problem (training needs search scores, search needs an
evaluation, the evaluation is the network) is broken with one piece of injected
knowledge: piece values, the same ones the move ordering already uses. Even
that lives in the data rather than in the engine. `NeraChessSelfPlay --mode
material` labels random play with material balance, which trains a
generation-0 network; every generation after that trains on the previous one's
games.

The whole loop is one command:

```bash
python3 scripts/pipeline.py --workdir runs/first --generations 5
```

Generation is written in C++ rather than here, because it needs legal move
generation, game-over detection, and a search per move — all of which the
engine already has, at roughly a hundred times the throughput a Python driver
plus a UCI round-trip per move would manage.
